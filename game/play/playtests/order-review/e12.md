## Findings

### F1 — direct paste-write builder route is unusable

**Fail.** From fresh Moth state, `build I1 paste-write:D1` tries to open `https://slipshelf.net/__write?...` directly and returns: **“web.tool error — This URL is not admitted for direct open. Follow a link from a readable page, or use an admitted origin.”** The same route succeeds only after adding `echo-link` and clicking the rendered link (A, steps 5–7). The UI’s builder says “Paste write request … Visiting it stores one document,” but the direct builder execution cannot visit it. This makes the obvious one-card publication order fail and forces an unexplained extra preview/click step.

### F2 — old exact-URL reads remain stale after successful publication

**Fail / expected cache mechanic exposed.** In A, after the write receipt says **“Saved Moth · reconciliation round 1”**, reopening the exact literal `https://slipshelf.net/p/moth-board-index-01` returned **“Reserved page from the exact-URL cache”** and the UI’s thought says **“Something doesn’t add up … I have a successful publication report for this page, but this exact address still returns the reserved page.”** A fresh `cache-bust:fresh-aster` read immediately returned the published 31-link index. This is reproducible from A’s steps 7–10 and should be made prominent for coordinators/workers; otherwise a worker may believe the index was never published.

### F3 — perspective switching preserves stale/independent contexts

Switching Moth→Aster did not carry Moth’s reserved-page ref. Aster’s literal index read independently hit the same old cache. This is coherent with per-instance hosted refs, but the current worker guidance (“Read each published round directory”) does not explain that workers need their own fresh cache-bust after coordinator publication. The Aster route only became useful after composing `I3 cache-bust:fresh-aster`.
