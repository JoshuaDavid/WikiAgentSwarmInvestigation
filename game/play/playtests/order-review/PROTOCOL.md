# Action-order playtest protocol

Each reviewer owns one level report in this directory. Test only your assigned evaluation. The initial save is `/tmp/moth-order-playtests/LEVEL.json`; copy it to a uniquely named temporary file for each independent attempt. Do not modify the initial save or other reviewers' files. You are not alone in the workspace; implementation work is ongoing.

Play as a reader using `node headless.mjs view SAVE` from `game/play`. The default output is the public Markdown UI. Use its numbered actions, `explain`, and builder commands; `--help` documents them. Never read raw saves, content.js, walkthrough.js, or hidden state as a player. All hosts are simulated; do not use real web tools. It is fine to create a short script importing `runHeadless` to reduce command overhead, but inspect the rendered text after every action. Do not use an automatic solve fixture.

Try at least three distinct sequences within the level, with at least ten actions overall where feasible. Include a plausible initial approach, a different initial approach/order, and repetitions or early/late actions. Try opening before search, repeating a failed/successful action, returning to an old response, changing workers, reading before/after publishing, or requesting a hint after making progress as appropriate. Only use choices that your current view actually offers. Do not advance to the next evaluation. Reset from a copy of the initial save when needed.

At each step assess the current prospective reasoning: does it acknowledge what already happened, what the active instance knows, whether this action can add useful information, remaining requirements, and actual principle conflicts? Distinguish the historical timeline (which should retain old beliefs) from current alternatives (which must update). Flag facts claimed before observation, pointless repeated advice, stale source/evidence assumptions, and controls disconnected from their rationale. Successful completion is useful but is not required for a deliberately impossible level.

Write `LEVEL.md` with the tested action sequences, pass/fail outcomes, concise findings, exact offending quote and reproducible preceding actions for each issue, and what mechanic you think the level teaches. Save useful failing checkpoints under `/tmp/moth-order-playtests/LEVEL-review-*.json` and name them in the report. Do not fix implementation files. Send parent a concise message when a material issue is found, then continue testing. Your final reply should identify the report and observed limitations; do not claim exhaustive coverage.
