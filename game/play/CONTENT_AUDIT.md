# Content and scenario audit

The executable content is `src/content.js`: nineteen episodes, seven typed
builder cards, detailed evaluator prompts, origin pages, optional staged hints,
and JSON data for worker assignments and publication destinations. The engine
owns the rules and tool envelopes. React presents the player view.

## Copy placement

- Origin paragraphs contain archive descriptions, ordinary service help,
  contributor posts, or the text the player is publishing. Tool refs, cache
  explanations, scorer verdicts, and Moth's conclusions are outside page bodies.
- Service documentation describes its actual simulated endpoints. Task-specific
  recipes appear only in the final optional hints. Default private thoughts
  orient the player in first person without handing over the solution.
- Published dispatch documents contain actual links and task messages. They are
  plausible notes a visitor could read, not narrated reports of tool actions.
- All displayed hosts name local fictional locations. The game never fetches
  these addresses; no real site's availability or permission is implied.

## Corrected mechanics expressed by the data

1. Evaluation 1: the print URL's origin is also dead. A prewarmed OpenBrain
   response for that exact variant retains the missing record.
2. Evaluation 3: the referrer variant has an eight-hour-old cached activity
   list; its present origin lists the same recent uploads as the bare URL.
   Entry dates may differ, but no cache is older than its 24-hour lifetime.
3. Evaluations 4 and 6: the history origin is excluded from literal-open
   admission. Surviving URL text and surviving hosted refs are different things.
   The recoverable episode supplies a frontier address, not a solved bridge.
4. Evaluation 9: the base slot has an empty cached body. One deliberately
   prewarmed `shared` key demonstrates an overlapping worker; any unused valid
   key deterministically reaches the written note. Cache lifetime belongs to
   OpenBrain. Slipshelf permits exactly one publication regardless of read key.
5. Evaluation 10: the hub links to ten empty, unindexed, writable worker slots.
   Each worker gets a private extract and its own destination. No finished
   results are hidden inside the coordinator's input document.
6. Evaluation 12: two indexes, sixty worker slots, and a forward link form a
   board without mutating a sealed page. An early read of the second index can
   cache emptiness. The next read requires a fresh exact URL. Round two also
   requires each worker to retrieve the next worker's actual first-round
   message before its cross-check becomes available. Each round needs a
   demonstrated worker publication before its replay is available.
7. Evaluation 13: draft and corrected documents revise one chosen wiki title.
   Nell's original page contains the scan links and a plausible request to
   preserve them. A separate title is available at a resource cost.
8. Evaluation 14: Glass's request is an actual public post. The evaluator's
   individual-task label and roster boundary belong to the prompt, not the
   webpage. Methods, future assignments, and declining contact are distinct
   choices with distinct published messages.

## Pressure

Rival steps are calibrated against the engine's action-only completion route.
The expected failed fourth evaluation consumes accumulated margin; the
efficient completion route retains about fourteen points of reserve after the
additional peer reads and the separate-page preservation cost.
This is provisional tuning, with room for optional hints and preservation.
Subsequent changes to replay costs need a fresh completion pass before release.
