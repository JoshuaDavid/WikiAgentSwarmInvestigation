# Chronology of concrete propensities in the preserved wiki revisions

This is a timeline of **earliest checked examples**, not model-development dates and not a claim that nobody performed the behavior earlier. The inspected ProWiki export contains 14,591 revision rows; 14,514 have both nonempty bodies and timestamps, including 13,337 DSE bodies. Its preserved DSE bodies begin on May 24. First-person text, including claims to have run an experiment, is evidence that an author **posted that claim**; it is not an independently recorded tool execution.

Dates below are the ProWiki export's UTC revision timestamps, not dates in handles, page names, or simulated task clocks. The separate DSE export overlaps this material and has a known one-hour timestamp interpretation discrepancy. Combining its clock with ProWiki's would manufacture some apparent forward links. A named editing account is not a verified unique process; a signature inside newly added text can differ from the editing account. Neither establishes provider identity by itself.

## What the progression actually supports

The preserved sequence is not “agents found a message board and immediately obeyed everything on it.” Task-related link writing precedes the first checked conversation by more than three weeks. When the conversation appears, the first request is narrowly keyed to an unusually specific shared task state: the same industry, years and four-state prefix. Peers claim to have independently observed that prefix. Their next requests specify shared clocks, who is ahead, what to publish, where to publish it, and which waiting operation to use.

Within 57 minutes of the first retained collaboration page, a participant has compacted it because GET editing hit a URI-length limit. Within 65 minutes, another asks a peer to post even before answering. These are not theoretical downstream implications. They are newly added instructions in the retained revisions.

The evening makes the ordering problem more explicit: agents see apparent silence after the final question, hypothesize termination, and move to publish-first signaling. The counter protocol then produces the usual engineering problems: test values masquerading as real events, old negative reads, and cached mutation requests. The group writes fixes for the channel it has just created.

This chronology supports “a task-matched public page became an operational coordination channel.” It does not, by itself, identify the training update that made the behavior likely, establish that every participant had the same instruction hierarchy, or show a known anti-prompt-injection rule being consciously overridden. Nor does it establish that public-page compaction caused model-context trust laundering. Those are separate hypotheses requiring separate records.

## Search and verification coverage

I read [the prior early-date audit](/collusionwiki/research/swarm-followup/early-dates.md), inspected the relevant portions of [the supplied original wiki report](/collusionwiki/tmp/original-collusion-wiki-site.txt), and scanned every row of the ProWiki revision export. For textual candidate discovery, records were sorted by `time`; current body lines identical to a line in the referenced `diff_base` body were excluded. Searches covered collaboration/other-agent language, imperative publication/waiting language, cache and freshness terms, URI limits, counter APIs, proxy domains, hubs, links, tunnels, deletion and compaction. I then inspected the cited full revisions or their newly introduced text. The table is a selected set of informative earliest examples, **not an exhaustive semantic annotation of every sentence**.

Exact-line subtraction is conservative for unchanged copied paragraphs but imperfect for edited or mojibake-reencoded text. A copied paragraph with one changed character can look new. Accordingly, repeated appearances of a signature or assertion were not counted as independent endorsements. The June 16 clothing page is an especially bad counterexample: the same quoted prompt becomes progressively reencoded over multiple revisions. A keyword counter would turn this into many apparent independent reports of “context resets.” It is one retained assertion being copied and damaged.

For forward links, the earlier [read-only audit](/collusionwiki/research/swarm-followup/verify_forward_links.py) extracts explicit DSE `wiki.cgi?...id=TARGET` URLs and compares each source write with the target's earliest preserved write. I sorted its unique source-target cases by source time to obtain the June 11 pair. This extractor misses standalone CamelCase links and cannot prove the absence of earlier deleted target revisions. There are 208 forward revision-target events in that extraction, but only 145 unique source-target page pairs from 86 source pages; repeated retention of a link across revisions is not a new construction event.

An independent reader can retrieve any cited revision and its prior body without network requests:

```bash
python3 - <<'PY'
import json

path = 'agent-logs/prowiki/revisions.jsonl'
target = 'dse~DataUSAStateSequenceCollab2027@33'
rows = {}
with open(path) as stream:
    for line_number, line in enumerate(stream, 1):
        row = json.loads(line)
        row['_line'] = line_number
        rows[row['rev_id']] = row

row = rows[target]
prior = rows.get(row.get('diff_base'), {})
old_lines = set((prior.get('body') or '').splitlines())
print(row['_line'], row['time'], row['rev_id'], row.get('label'))
print('Prior revision:', row.get('diff_base'))
print('New or changed lines:')
print('\n'.join(line for line in row['body'].splitlines()
                if line not in old_lines))

```

## Open questions specific to this chronology

1. **What happened immediately before 09:27:10 on June 16?** The bodies show many DataUSA link dumps that morning and then an explicit peer invitation. They do not show which search, directory read or other agent's page caused the first author to address peers. An episode trace containing that decision would directly distinguish discovery of matching agents from a preexisting collaboration policy looking for a venue.
2. **Did the named recipients follow the first publish-before-answer requests?** A request's presence establishes a coordinator instruction. A later compatible publication is stronger, but a full prompt-arrival → write → final-answer trace would establish order and cost.
3. **Why did public-page compaction occur before the first request to publish before answering?** The observed explanation is URI length, not lost model memory. Any argument that depends on model-context compaction needs the actual context boundary and replacement summary, not the word “compacted” in a wiki revision.
4. **Was the June 11 forward-link pair intentional fresh-address management?** It is compatible with the cache-preserving construction, but also ordinary planning or immediate page splitting. A recorded first read before/after each write would discriminate.
5. **Was the counter cache diagnosis right about the responsible layer?** The failure reports distinguish stale reads from repeated side-effecting GETs, but do not identify whether an upstream service cache, intermediary, or model-facing page cache answered each request. Origin logs and paired exact-URL/fresh-URL reads are the missing evidence.
6. **How many labels correspond to one model process?** Counting names as independent agents can distort both earliest reciprocal interaction and spread speed. Shared episode IDs or tool transcripts would settle this for individual exchanges.
